Overview
You need to build a simulation of an infectious disease spreading through a population, and
then use it to study parallel and asynchronous execution. The challenges are:
• parallelising it correctly, so that results are identical for any number of threads;
• using asynchronous programming to overlap computation with slow work;
• carrying out a careful study of performance at several levels of parallelism.
No locks, semaphores or condition variables are required. The only coordination
you need is starting tasks and waiting for them to finish (thread join, or waiting on a future).
2
The Model
2.1
Population and states
The population is an N × N grid with one person per cell. Each person is in one of four states:
• S (Susceptible): healthy, can be infected.
• I (Infected): sick and contagious. Also stores c, the number of days infected.
• R (Recovered): immune.
• V (Vaccinated): immune
• D (Dead).
Each person’s neighbours are the eight surrounding cells. Cells outside the grid do not exist;
the edges do not wrap around.
2.2
Update rules
The simulation advances one day at a time. All cells are updated together: the state on day
t + 1 depends only on the state on day t.
1. Infection. A susceptible person with k infected neighbours becomes infected with prob-
ability
P(k) = 1 −(1 −βeff)k
where βeff is the current transmission probability. A newly infected person starts with
c = 0.
2. Progression. An infected person’s counter c increases by one. When it reaches d, the
person dies with probability µ, and otherwise recovers.
3. Recovered and dead people never change state.
1
2.3
Initial conditions
First, a fraction v of the population, chosen at random, is vaccinated (set to V). Then I0
susceptible people, chosen at random, are infected. This setup may be done sequentially.
2.4
Interventions
The main thread changes βeff between days, using the daily totals:
• Masks: βeff = β × m for the whole run, where 0 < m ≤1.
• Lockdown: when the infected fraction rises above θon, multiply βeff by λ. Lift the lock-
down when the infected fraction falls below θoff.
A decision made from day t’s totals
applies from day t + 1.

3
Concurrency Rules
1. Two grids. Keep a current grid and a next grid. During a day, threads read only from
current, and each thread writes only its own cells of next. Swap the grids after all threads
have finished. Explain in your report why this design has no data races.
2. Each cell updates itself. A cell decides its own next state by reading its neighbours. It
never writes to a neighbour.
3. Only join or wait. Use only thread join or waiting on futures. If you use anything else
(locks, atomics, barriers), justify it in your report.
4. Local counts. Each thread counts S, I, R, V and D in its own part of the grid and returns
the counts. The main thread adds them up.
3.1
Random numbers
A single shared random generator would make results depend on thread timing. One generator
per thread would make results depend on the number of threads. Neither is acceptable.
Instead, compute every random number from a hash of (seed, day, cell, stream), where stream
separates different decisions (0 for infection, 1 for death). The result then depends only on which
cell and day it is, not on which thread computes it. function is given in Appendix B.

Correctness requirement: for the same seed and parameters, your program must produce
exactly the same output for every number of threads, every way of dividing the grid, and both

Part B: Threaded version (20 marks)
1. Thread per day. Each day, split the grid into C strips of rows, start one thread per
strip, and join them all before swapping the grids. Use lambda function where necessary.
2. Thread pool. Create a pool of T threads once. Each day, submit C tasks (C may be
larger than T) and wait for all of them to finish.
3. Ways of dividing the grid. Support strips of rows, square blocks, and interleaved rows
(thread i takes rows i, i + T, i + 2T, . . . ).
4. Testing. Write a script that runs the program with T = 1, 2, 3, 4, 7, 8, 16 and every way
of dividing the grid, and checks that every CSV file is identical to the sequential one.
Commit Part-B on a single branch.

Part D: Performance study (20 marks)
Follow the method in Section 5. For each experiment, give a graph and explain the results.
D1.
Strong scaling.
Use N = 4000, 200 days, no snapshots. Measure the time for T =
1, 2, 4, . . . up to twice the number of logical cores. Plot speedup and efficiency. Calculate the
Karp–Flatt serial fraction (Appendix C) and compare with Amdahl’s law. What happens beyond
the number of physical cores?
D2. Weak scaling.
Keep the work per thread fixed (e.g. 1000 × 1000 cells per thread) and
increase the grid size with T. Plot efficiency and relate it to Gustafson’s law. If you do not
reach the ideal, explain why (consider memory speed and caches).
D3. Size of work units.
1. With T equal to the number of physical cores, vary the number of chunks C from T to
64T. Find the best value and explain why.
2. Compare the three ways of dividing the grid.
3. Compare thread-per-day with the thread pool for small grids (N = 50 to 1000). Find
the smallest grid size at which the parallel version is faster than the sequential one, and
explain why.
D4. Parallelism within a run vs. across runs.
Using P cores (your number of physical
cores), complete 32 independent runs from the sweep in C2. Try different ways of using the
cores: R runs at once, each with T threads, where R × T = P (for example 1 × 8, 2 × 4, 4 × 2,
8 × 1). Measure the total time and the runs completed per second. Which is best, and why?
Consider the overhead of threads within a run, runs that last different numbers of days, and
memory use.
D5. Hiding I/O time.
Compare the total time with no snapshots, blocking snapshots and
asynchronous snapshots, for different values of --io-latency and K. How much of the writing

How to Measure Performance
• Report your hardware: CPU model, physical and logical cores, cache sizes, memory, op-
erating system, and compiler or Java version.
• Time only the simulation loop, not setup or output (except in D5).
• Repeat each measurement at least 5 times and report the median and the spread.
• Close other heavy programs, and use the same machine for all experiments.
• Use scripts, so that all experiments can be repeated.

futures = []
